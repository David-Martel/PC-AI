# Process Lasso and live media: primary-source research

Research date: 2026-10-05. Scope: read-only vendor/documentation review. Recommendations below are proposals, not applied settings or measured performance gains. Hardware topology, running-process attribution, and policy state belong to the accompanying local evidence. No application, registry, power-plan, network, or service settings were changed in this lane.

## Recommended policy and its limits

1. **Keep the useful compute workload productive.** Use ProBalance as the starting contention control. Bitsum recommends small temporary reductions for CPU-heavy background activity and cautions against High/Realtime boosts. Classify work by purpose and session, rather than demoting every `python`, `node`, `pwsh`, or compiler process. Preserve agent, git/gh, build, and evaluation throughput as explicit measured outcomes. [ProBalance](https://bitsum.com/how-probalance-works/).
2. **Restore app scheduling defaults before adding boosts.** For live Zoom, Teams, NVIDIA Broadcast, audio and capture, first compare the present policy against removal of custom persistent CPU/I/O/GPU overrides. App-selected priorities and Windows multimedia scheduling form the baseline. A bounded Above Normal CPU trial is a later experiment only if thread ready-time pressure coincides with call glitches; reject it if useful compute throughput or media quality worsens. Do not force arbitrary priorities on `audiodg`, DWM, driver hosts, or all WebView2 processes. MMCSS lets participating application threads request time-sensitive CPU treatment; do not infer participation for a particular binary without a trace. [Microsoft MMCSS](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service).
3. **Treat live media processing as useful work.** Broadcast microphone/camera effects can legitimately compete for the GPU. Test effects independently and compare minimal necessary effects with the current set. NVIDIA permits multiple effects up to the GPU's capacity; that does not establish how much spare capacity this workstation has. Avoid stacking the same denoise/background effect in Broadcast and a meeting application without checking which pipeline is active. [NVIDIA Broadcast FAQ](https://www.nvidia.com/en-us/geforce/broadcasting/broadcast-app/faq/).
4. **Do not use memory trimming as a RAM-capacity fix.** Track commit, private bytes, resident private working set, available memory, and hard-fault I/O separately. SmartTrim evicts residency; it does not release the application's committed allocations. Hot pages return when used. Default to no forced trimming of live media or active inference. Persistent pressure calls for less duplication, bounded concurrency, smaller model/cache footprints, or capacity changes. [Bitsum FAQ](https://bitsum.com/process-lasso-faq/), [Windows working sets](https://learn.microsoft.com/windows/win32/memory/working-set).
5. **Use memory priority only for genuinely cold background data.** It is an eviction-order hint. A lower priority can suit bulk indexing/data that is unlikely to be reused soon; it does not cap memory and can hurt a hot cache. Leave call and hot model pages at application defaults. Measure hard-fault count and I/O time before and after any experiment. [Microsoft memory priority](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation).
6. **Retain scheduling flexibility.** If a verified hybrid topology shows a scheduling problem, compare a soft CPU Sets preference with unrestricted scheduling. Hard affinity is a resource limit and can restrict throughput. Do not assume CPU-number ranges identify P/E cores without local enumeration. Avoid reserving cores or driver-interrupt affinity experiments during this review. [Bitsum CPU Sets](https://bitsum.com/apps/process-lasso/docs/rules/cpu-sets/).
7. **Efficiency Mode is a targeted experiment.** It signals that work is not time critical and can affect power/core selection. Use ON only for known low-value background work. An OFF rule on an entire process also removes thread-level efficiency classifications that the application may intentionally use. Keep ProBalance's additional Efficiency Mode action out of the initial baseline; Bitsum says it is heavier than ordinary restraint. [Efficiency Mode](https://bitsum.com/apps/process-lasso/docs/rules/efficiency-mode/).
8. **Test power mode under sustained load.** Performance Mode can engage a more aggressive power plan. Compare 30+ minute AC-powered sessions and record temperature, frequency, power and fan/thermal behavior, not just a brief CPU burst. A continuously running chat application is an unsuitable proxy for “currently in a meeting.” Gate any meeting policy on explicit session state, with restoration at call end. [Setup guide](https://bitsum.com/apps/process-lasso/docs/getting-started/setup-guide/).

## CPU, GPU, disk, and network priority are separate

Current Process Lasso has GPU scheduling priority rules; CPU priority alone is not a substitute. GPU rules are not inherited by children. I/O priority is a hint without guaranteed QoS. Leave Windows dynamic thread boosts enabled by default. Inventory registry-enforced CPU/I/O/memory priorities as well as the INI, because they can persist outside the current configuration. Limit any GPU-priority experiment to verified media processes and compare it against useful inference throughput; a rule is not a VRAM reservation or a demonstrated latency guarantee. [Bitsum priorities](https://bitsum.com/apps/process-lasso/docs/rules/priorities/).

There is no documented Process Lasso setting here that substitutes for Teams network QoS. Microsoft uses DSCP plus classification/queuing across the managed network. Client markings alone do not establish end-to-end prioritization. Verify port ranges, actual packet marking, and the NIC/switch/AP/router path before proposing a network change. [Teams QoS architecture](https://learn.microsoft.com/en-us/microsoftteams/qos-in-teams).

Microsoft's current Windows client examples target `ms-teams.exe`, not the old `Teams.exe`. Default source-port classes are audio 50000–50019/DSCP 46, video 50020–50039/34, sharing 50040–50059/18, and calling/meeting signaling 50070–50089/40. Tenant-customized ranges must be checked. Do not apply these ranges to Zoom or mark every Teams packet as audio. [Teams client QoS](https://learn.microsoft.com/en-us/microsoftteams/qos-in-teams-clients).

## Configuration interpretation: numeric EfficiencyMode

**Local evidence correlates `EfficiencyMode=<process>,0` with OFF on installed Process Lasso 18.4.1.3.** The accompanying [policy snapshot](policy-snapshot.json) records zero-valued Zoom/Chrome rules, installed binary versions, and `SafePolicyEvents` explicitly reporting `Efficiency Mode OFF` for those processes. This resolves the local interpretation for those observed rules; do not describe them as forced EcoQoS ON. The vendor rule page explains semantic ON/OFF and the Rules column documents `E` versus `e`, but the retrieved INI reference does not specify numeric encoding. The linked February 2025 JSON schema does not define `efficiencyMode` either. A vendor-author forum example contains zero without declaring its polarity. Vendor encoding documentation remains absent, so this local correlation should not become a universal future-version parser contract.

For current effective state or a future installed version, inspect process power-throttling state through Windows `GetProcessInformation` and correlate configured GUI rule labels/Rules columns as needed. Thread-level behavior and current process behavior can differ from a saved persistent rule or a historical policy event. If a future encoding check requires a controlled export comparison, use a separate disposable configuration and test process; do not invert live call/terminal settings speculatively.

## Measurement plan: sufficient coverage, not just elapsed time

This is an experiment design, not a vendor-prescribed duration or evidence that data has already been captured.

### Continuous low-overhead baseline

Capture an initial three working days, as selected by the user, with normal agent/build/evaluation activity. Extend if representative coverage is incomplete: aim for at least three actual Zoom meetings and three Teams meetings when both applications are actually used. If an application is unused during capture, retain that coverage gap instead of manufacturing confidence. Include startup/logon, cloud synchronization, long calls, camera/effects, audio-only, screen sharing, AC versus battery if used, and ordinary idle periods. Mark actual session starts/ends and anomalies in UTC with purpose labels. A brief current snapshot can identify candidates, not sustained waste.

Use the measured 30-second continuous cadence without GPU counters; faster 10-second or focused captures require a fresh observer-overhead check. The [measurement plan](measurement-plan.md) is authoritative for cadence and current collector coverage. Save CPU deltas/time-normalized rates, PID plus creation time and sanitized role/parent context. Reused PIDs and app process trees must not be conflated. Continuous collection covers private bytes, working set, handles and generic I/O byte deltas; system commit/limit, available RAM, page reads, disk latency/queue and adapter throughput. Extend focused profiling for thread scheduling, short-lived starts/exits, I/O operations, NIC errors and GPU engine/memory observations when needed. Process I/O bytes are not proven process network bytes. Total page faults include soft faults and are not a hard-fault substitute. Do not add all process working sets as physical RAM consumption: shared pages overlap.

Judge waste by resources per useful completed unit and by sustained resources during verified no-purpose intervals. Multiple child processes do not by themselves imply duplicated work. Investigate repeated polling, reconnect loops, repeated repository scans, duplicated model residency, redundant MCP/server sessions and startup churn. Pool or share only where authentication, lifecycle, isolation and protocol semantics permit it. For owned WebView2 software, Microsoft recommends environment reuse; an operator cannot safely fuse unrelated third-party application process trees. Keep GPU acceleration unless a specific fault is being diagnosed. [WebView2 performance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance).

### Meeting-quality evidence

Zoom's client statistics expose app/system CPU and audio/video/share statistics. Record quality during a session with the exact camera, effects, layout, screen-share mode, link and competing workload; CPU reduction alone is not an acceptable outcome. [Zoom statistics](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0070504).

Prefer Zoom's supported local Autosave QoS Stats for longitudinal correlation. It produces timestamped JSON lines with audio/video/share latency, jitter, loss, resolution/frame rate and Wi-Fi RSSI. It can be enabled in the Network Connectivity Tool or with the documented `Zoom.exe --qlog=on` option, and disabled with `--qlog=off`. Enabling it changes application behavior and remains a proposal in this read-only lane. Rotation retains only the latest four files, with a maximum of 50 MB per file; collect sanitized numeric data after each call before overwrite. Raw filenames/logs can contain meeting identifiers. Zoom does not provide ingestion/reporting support for these logs. [Autosave QoS documentation](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0077003).

Teams Call health provides in-call media/link observations. Keep each direction/modality distinct and correlate timestamps with system sampling. [Teams Call health](https://support.microsoft.com/en-us/teams/meetings/monitor-call-and-meeting-quality-in-microsoft-teams).

Teams admin Real-Time Analytics documents audio good thresholds of jitter below 30 ms, packet loss below 5%, and RTT below 500 ms, plus hardware encoder/decoder failure, source freezes, app CPU and recovery data. These are troubleshooting thresholds, not stringent optimization goals. Set experiment goals below the present baseline, retain p95/p99 and burst loss, and count user-visible glitches. Tenant licensing/roles may limit admin telemetry. [Teams real-time telemetry](https://learn.microsoft.com/en-us/microsoftteams/use-real-time-telemetry-to-troubleshoot-poor-meeting-quality).

The former Teams-memory article now redirects to network preparation. Do not use old Electron-era statements as evidence for current Teams behavior. Current Teams requirements reference WebView2; vendor comparative performance claims are not proof for this workstation. [Current client requirements](https://learn.microsoft.com/en-us/microsoftteams/teams-client-system-requirements).

### Targeted ETW for causes

Use short bounded WPR traces around a reproducible glitch (typically 2–5 minutes with a brief lead-in), rather than collecting full-detail ETW for a week. Context7 was resolved to the official Windows Performance Toolkit corpus and queried for current capture/analysis guidance. Enumerate installed profiles before choosing them; the available capture is not determined by a remembered profile name. WPR exposes profile enumeration and recording status including dropped events. [WPR command reference](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpr-command-line-options).

Memory logging uses circular buffers and overwrites earlier events. File logging is sequential and can grow until storage is exhausted. Keep trace duration/storage explicit, inspect event loss, and do not cancel another session's recording. Measure collector overhead using matched runs with and without collection. [Logging modes](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/logging-mode).

Choose resource profiles for CPU, disk/file/network I/O and memory as needed; enable detailed allocation tracing only for a specific memory-lifetime question. [Resource-based recording](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/recording-for-resource-based-analysis).

Analyze sampled CPU stacks to identify work; precise CPU/context switches to distinguish running from waiting/ready; DPC/ISR time by module/function to find driver interference. Priorities act on schedulable threads and do not fix a driver spending excessive time at interrupt level. Correlate driver events with actual audio/video/UI glitches before identifying a culprit. [Microsoft CPU analysis](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/cpu-analysis).

WPA provides hard faults by process/file and I/O time, commit lifetimes, process lifetimes, GPU utilization and frame-related graphs when those events were captured. Inspect hard-fault backing-file identity: mapped-model/file reads are not necessarily pagefile pressure. A graph absent from a trace is missing coverage, not zero activity. [WPA graph inventory](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/list-of-wpa-graphs).

### Promotion criteria

Run at least three matched repetitions of each controlled comparison, separating cold and warm caches. Match meeting layout/effects, network path, model/task, useful concurrency and power conditions. Change one policy class per experiment. Suggested decision gates: no additional audible glitches/freeze bursts, improved or unchanged media p95/p99 quality and UI latency, no commit/hard-fault regression, and useful agent/build/evaluation throughput within a pre-agreed tolerance (initial proposal: 5%). Report sample counts, missing counters, collection overhead and uncertainty; small or poorly matched samples are provisional. Retain exported before/after configuration, exact binary versions, experiment timestamps and rollback plan before promoting a setting.

For battery trials, include presence/input state in the record: current Windows documentation says inactivity can lower foreground QoS and skew automated benchmarks. The same documentation distinguishes Media/Deadline QoS for multimedia threads and identifies audible processes as HighQoS. This strengthens the case for app/system defaults before whole-process overrides. Do not turn a documentation note into an unsolicited global registry change. [Windows CPU QoS](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service).
