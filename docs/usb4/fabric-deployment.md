# USB4 fabric deployment and interface roadmap

Status: proposed increment plan; implemented and unqualified behavior are separated below. PC-AI is the code home. Existing Windows and Linux controllers remain the starting point. This document does not authorize clearing retained ownership state or replacing the working Thunderbolt Share connection.


## Current architecture checks

The [USB4 workflow](../../.github/workflows/usb4-lifecycle.yml) retains native x64 contract execution and adds `cargo check --all-targets` for the matching host's ARM64 target. Windows uses `aarch64-pc-windows-msvc`; Linux uses `aarch64-unknown-linux-gnu`. This is deliberately not a Linux-to-MSVC build. Installing a Rust target supplies its standard library, not every SDK/linker. Check-only runs can still execute host build scripts or require native prerequisites; failures are not converted to unsupported success.

## Intent and current source

Provide reliable, bidirectional peer connectivity over OS USB4 networking, with explicit ownership, observable service readiness and predictable reconnect/upgrade behavior. Intel Share is a product reference for file transfer, synchronization, migration and shared desktop/input; none of its licensing or private APIs is a runtime dependency. The first deployable scope is transport and routing. Desktop, clipboard and file access are distinct capabilities, not permissions granted by a connected cable.

Existing source: [fabric_plan.rs](../../Native/pcai_core/pcai_tb_cli/src/fabric_plan.rs) projects fresh reciprocal adjacency without mutation or authentication; [edge_policy.rs](../../Native/pcai_core/pcai_tb_cli/src/edge_policy.rs) derives enrolled Linux edge identity and ULA proposals; [edge_observer.rs](../../Native/pcai_core/pcai_tb_cli/src/edge_observer.rs), [nm_edge.rs](../../Native/pcai_core/pcai_tb_cli/src/nm_edge.rs), [networkd_edge.rs](../../Native/pcai_core/pcai_tb_cli/src/networkd_edge.rs) and [edge_probe.rs](../../Native/pcai_core/pcai_tb_cli/src/edge_probe.rs) implement Linux observation, adopted configuration and pinned source-bound qualification. Windows uses [Invoke-Usb4PeerNetwork.ps1](../../Tools/SystemScripts/Networking/Invoke-Usb4PeerNetwork.ps1) and its installer. Its Peer/Provider/Consumer policy differs from the Linux enrollment schema; they must not be called interchangeable today. The existing installed Windows r5 controller is sourced from commit `069a61264eb930fc914ed3ee8c54ea4823bfe9ea` (controller SHA256 `fb368a133d99c4e99784c31d7277bc8bdd45e302b26a8d00b4e7f7b65780a3ed`), preserved unchanged in draft PR233 head `217707ee2bfa5b7a7d640d0b70a05bd79ae1c090`. It is ahead of the controller at review baseline `4e33b63a4aaba2083ed4fbce524a835d6cbcd7bb` and retains an unresolved recovery journal. Private machine custody evidence remains outside publication; the exact source revisions identify the restoration candidate, not permission to deploy it.

## Interface and trust

A future common interface reports separate dimensions: observation and freshness; enrolled identity and revocation; desired/actual configuration; pending ownership; transport proof; authenticated service proof; supported application capabilities. A single green connected indicator must not collapse those facts. Every error includes its scope and retry/review reason. Planned, applied and verified are distinct results. Existing `ObservedUnverified`, `ENROLLED_UNVERIFIED`, `ACTIVE_UNVERIFIED` and `CONFIGURED_UNVERIFIED` remain truthful source states, not equivalent readiness.

My implementation choice is a native Rust domain/control layer with small OS backends and a separate user-session interface. Reuse pinned management identity for initial enrollment: independently verify both host identities, bind approved controller/interface incarnations and allocations, and retain revocable per-peer trust. Reciprocal MACs, controller UUIDs, hostnames, banners and bus messages alone do not authenticate a peer. Reconnect can reuse previously authorized trust; a replacement device, changed policy epoch, revoked identity or unresolved ownership requires review. Do not invent a new cryptographic pairing protocol. Data services use maintained authenticated protocols and their own user/ACL checks.

Proposed UI actions are inspect, preview, enroll/revoke peer, choose approved capabilities, apply an explicit plan, inspect recovery and export a redacted diagnostic. Privileged routing runs outside the user-session agent. Desktop capture/input/clipboard stay in user sessions using platform consent/session APIs. Linux Wayland portals and Windows capture/input restrictions are capability boundaries; unattended privileged input injection is not assumed. No GUI or common service API currently exists, so these actions are design, not available commands.

## Lifecycle and routing

Events enqueue bounded recollection rather than mutating inside OS callbacks. Initial registration is followed by a complete inventory; events are coalesced and a periodic fallback repairs missed events. Stale work is discarded on policy/boot/device-incarnation mismatch. Windows resolves enrolled interface GUID to current NET_LUID; interface index is an observed handle, not persistent ownership. NET_LUID must not be described as boot-ephemeral. Notifications may have incomplete/null rows and require fresh queries; cancellation is outside callback/dependency threads. Linux uses rtnetlink or NetworkManager D-Bus according to the existing owner, never two independent writers for one configuration. Interrupted dumps resynchronize before decisions.

Default policy is direct peer connectivity without default-route, DNS, bridge, forwarding or NAT adoption. A policy can explicitly request reviewed owned routes and metrics. Effective Windows metric includes route plus interface metric. Route preference changes need hysteresis, source-qualified return-path evidence and preservation of an independent management path. Transit, bridging and internet Provider/Consumer roles require separate allocations and ownership. A USB4 router tree is not proof of one Ethernet broadcast segment. IPv6 link-local targets use the outgoing local interface scope.

Each enrolled edge needs isolated policy, immutable revision, task/service identity, state, journal and reports. Keep global mutation serialization while rollback compares whole-host routes/addresses/DNS/NAT and global resources remain shared. A different directory or per-edge mutex alone does not establish independence. Preserve pending transactions and original preimages; no reset-by-deleting-state. Repeated reconciliation must be idempotent and must not modify foreign routes, profiles, services or vendor state.

## Proposed ownership and bilateral admission contract

These are requirements for the successor coordinator, not features present in the current scripts. Use an opaque stable enrollment UUID as the management key, bound immutably to both enrolled host identities and an explicitly versioned endpoint-identity record. Keep the existing Linux controller-pair edge ID in its own namespace and keep observation IDs separate. Interface incarnation, policy epoch and current addresses are fields, not reasons to silently rename a persistent enrollment. Windows tasks and roots derive from the validated enrollment key; every manifest binds that key and exact policy/state/report paths. Legacy singleton enrollment remains reserved, with its existing task/root/journal unchanged until an explicit compatible migration is reviewed.

Choose one host-level mutation coordinator and reservation registry. Before apply, install, upgrade, repair or uninstall, it acquires the host coordination lock, rejects pending/unknown journals, checks exact reservation ownership, and quiesces only its owned affected tasks under a defined lock order (installation coordination, then network mutation). Compare the task/pointer preimage again immediately before replacement and read it back afterward. Current installer, controller and legacy reconciler use different mutexes; this is not yet cross-writer coordination. Until every participating writer is enrolled in that protocol, refuse overlap with an enabled/active legacy or foreign writer rather than assume a new mutex protects it. Never disable an unrelated required link to gain the lock.

Reserve interfaces/incarnations, prefixes/allocations, profiles, shared uplinks, task identities and state roots exactly once. Reject task/root/state reuse or overlapping reservations under different enrollment keys. Global ICS/WinNAT reservations remain global. For Linux retain one host coordinator/service authority over the policy collection, with edge-keyed state/status underneath it, rather than duplicate current units that share /etc/pcai-usb4/policy.json and operation-named status files. Additional unit instances require explicit instance-safe paths and the same reservation authority before activation.

Each endpoint durably accepts a monotonically increasing enrollment-policy epoch and exact hash, with disjoint IPAM admission recorded before applying either side. Same epoch/different hash and lower epoch are refused; global IPAM and durable epoch enforcement are future work, not supplied by the current planner. Authenticate and prove the source/interface/return path independently in each direction; one successful Linux-to-Windows probe is not bilateral readiness. Management enrollment uses the operator identity, while scheduled SYSTEM/host services use their own least-privilege restricted principal and key custody, never an assumption that interactive user credentials transfer.

If only one endpoint stages, applies or upgrades, expose asymmetric readiness and retain both endpoints' available transaction IDs/preimages. Do not compensate on an unverified remote endpoint or remove its state. Continue only local owned rollback when its exact preimage/current-state guard permits it; otherwise hold. An old reader must not execute against a newer or unknown policy/journal schema. Explicitly inventory the existing schema1 readers during extraction, preserve incompatible state unchanged, and require a reviewed migration for any new coordinator schema. Artifact rollback does not roll back policy epoch or erase an accepted newer journal.

## Installation, upgrade and compatibility

Promote reviewed source before deployment. Separate artifact release identity/source/build target from host-specific enrollment/configuration identity. A release manifest binds source revision, artifact bytes, size, hash, host/OS/architecture and relevant runtime requirements; source provenance and authentication/signing remain separate from an arbitrary manifest's self-consistency. For an unsigned release, bind an approved expected hash to reviewed source; a self-declared source string is not independent provenance. Require an explicit policy/journal compatibility declaration before execution. Stage immutable revisions, verify before replacing a task/service pointer, retain original ACL/ownership and rollback preimages, and read back exact service arguments and installed bytes. Reject stale/foreign revisions and pending custody before activation. An upgrade never silently changes role or enrolls a new peer. Uninstall/repair must use the same ownership checks and preserve failed recovery artifacts.

First restore only the optional installer release binding and four matching installer control groups from commit069a612/draft233 as a narrow reviewed change; do not copy the older controller from main into r5. The narrow [release-binding PR](https://github.com/David-Martel/PC-AI/pull/291) records extraction and subsequent ordering/schema controls; inspect its exact reviewed commit when available. Then independently review the 069a612 controller reporting/default-route delta and the publisher/doctor/catalog/test dependency closure. Preserve draft233's additional55-line autocrlf source-canonicality control and only its two release-specific LF attribute rules if extracting that publisher. Full PR233's coverage/integration hold remains separate. Only then add per-edge installation identity while preserving legacy singleton compatibility. Existing r5 must not be downgraded or reassigned during this source integration.

Use Windows USB4NET/OS connection-manager drivers and Linux thunderbolt_net. Near-driver implementation means supported IP Helper/netlink/D-Bus notifications and route APIs, ETW/perf tracing and fresh device ancestry, not a new unsigned driver. Windows x64, Windows ARM64, Linux x64 and Linux ARM64 receive separate compile, portable-contract, installed-service and hardware records. Cross-compilation is evidence of build compatibility only. Intel Share ARM64 support is not established; Linux Kconfig eligibility does not qualify ARM hardware. Unsupported platforms/features remain explicit.

## Measurement and staged delivery

Measure fixed-source sequential upload/download, simultaneous directions, latency/jitter, CPU, reconnect/resume time and observer overhead. Retain payload size, duration, exact endpoints/interfaces, software/build identity and before/after configuration. Nominal link speed and a TCP handshake are not authenticated file-transfer throughput. Preserve MTU/offloads until measured evidence justifies a reversible tuning change. Bound traffic, output and runtime; keep benchmarks opt-in and outside active HIL sessions. Use NTTTCP/iperf-style transport tools as qualified on each host, actual authenticated copy separately, and ETW/perf only for a concrete question.

Execution boundary: this design was reviewed during a Gen9/Gen7 HIL hold prohibiting local builds, tests, heavy jobs, device scans/connections, app starts and network/runtime changes. Check current fleet ownership before validation. While such a hold is active, source review/editing and permitted remote CI may progress; publication does not qualify installed behavior.

Delivery order: (1) truthful Linux operational exit/evidence contract, (2) Windows release binding and release-safe source integration, (3) per-edge task/state identity and verified upgrade/rollback, (4) explicit architecture compile coverage, (5) event-driven observation with missed-event recovery, (6) controlled bilateral Peer installation and physical reconnect/resume/reboot qualification, (7) user-session capabilities and accessible UI. Each PR is narrow, reviewed at its exact head, and merges only through the existing autopilot. Installed-service/hardware gates remain distinct from portable fixture success. Active foreign worktrees/WIP remain held until exact source equivalence, owner disposition and ignored-data custody are established.
